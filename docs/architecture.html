Peta arsitektur Komunifind

Penjelasan sederhana tentang bagaimana aplikasi ini disusun: siapa bicara dengan siapa, di mana aturan bisnis disimpan, bagaimana data mengalir, dan kenapa diputuskan begitu. Ditulis untuk dibaca tanpa harus buka kode.

Next.js + Go + Postgres Docker Compose nginx 1 VPS Skala <500 user

1. Ikhtisar singkat

Tiga kalimat yang cukup untuk paham sistem ini.

Apa ini

Direktori komunitas

Pengunjung bisa mencari komunitas dan melihat event tanpa akun. Untuk mendaftar event, user login dengan Google. Panitia mengelola komunitas dan event-nya sendiri lewat dashboard.

Aturan emas

Go pemilik aturan, Next pemilik tampilan

Semua keputusan bisnis (kuota, status pendaftaran, akses per komunitas) hanya ada di Go. Next hanya merender halaman, mengurus login Google, upload file, dan mengirim email.

Kenapa dipisah

Biar tidak berantakan

Kalau aturan bisnis tersebar di dua tempat, cepat atau lambat keduanya berbeda. Dengan satu pemilik aturan, bug lebih mudah dilacak dan perubahan lebih aman.

Cara akses

Browser cuma kenal Next

Browser tidak pernah memanggil Go secara langsung. Next meneruskan permintaan ke Go sambil membawa token dari cookie. Tidak ada CORS, token tidak pernah terlihat oleh JavaScript browser.

3. Alur utama

Empat skenario yang paling sering terjadi.

A. Pengunjung membuka halaman

  1. Browser membuka http://localhost:8088/.
  2. nginx meneruskan ke container Next.
  3. Next (server-side) memanggil Go: daftar komunitas, filter, dan event terdekat.
  4. Go membaca Postgres, mengembalikan JSON.
  5. Next merender HTML lengkap, lalu mengirim ke browser.
  6. Di browser, animasi scroll dan carousel dijalankan sebagai lapisan tampilan saja.

B. Login dengan Google

  1. User klik “Masuk”. Next membuat state acak dan mengarahkan ke Google.
  2. Google mengembalikan code ke /api/auth/google/callback milik Next.
  3. Next menukar code menjadi ID token, lalu mengirimkannya ke Go.
  4. Go memverifikasi tanda tangan, audience, dan masa berlaku token.
  5. Go membuat/memperbarui user, lalu menerbitkan JWT (7 hari).
  6. Next menyimpan JWT di cookie kf_session yang HttpOnly, lalu mengarahkan sesuai role.
  7. Setiap permintaan berikutnya: Next membaca cookie dan mengirim header Authorization: Bearer ke Go.
Kenapa aman Token tidak pernah menyentuh JavaScript browser. Middleware Next hanya dipakai untuk redirect tampilan; pengecekan role dan kepemilikan data tetap dilakukan Go di setiap request.

C. Daftar event (kuota + approval)

pending approve → approved cancel → cancelled
pending reject → rejected daftar lagi → pending
  1. User klik “Daftar event”. Next meneruskan ke POST /events/:id/registrations.
  2. Go memastikan event terbit, belum mulai, dan kuota belum penuh. Baris pendaftaran dibuat dengan status pending.
  3. Panitia membuka dashboard, melihat daftar peserta, lalu menekan “Setujui”.
  4. Go mengunci baris event (SELECT … FOR UPDATE), menghitung ulang jumlah peserta disetujui, baru menyimpan approval.
  5. Jika kuota penuh, approval ditolak dengan pesan jelas.
  6. Next mengirim email pemberitahuan (best-effort) dan mencatat hasilnya.
Kenapa pakai FOR UPDATE Dua panitia yang menekan “Setujui” bersamaan tidak bisa menembus kuota, karena penghitungan dan penyimpanan terjadi dalam satu transaksi yang dikunci per event.
  • Satu user hanya punya satu baris per event; batal berarti mengubah status, bukan menghapus.
  • Batal dari status disetujui otomatis membebaskan slot, karena kuota dihitung ulang.
  • Status “disetujui” tidak bisa ditolak; kalau perlu keluar, user membatalkan sendiri.
  • Kuota tidak bisa diturunkan di bawah jumlah peserta yang sudah disetujui.

D. Upload gambar

  1. Panitia memilih file di form dashboard.
  2. Next memvalidasi tipe (JPG/PNG/WebP) dan ukuran (maks 5 MB).
  3. Next mengecilkan dan mengubah file menjadi WebP memakai sharp (logo maks 512px, lainnya 1600px).
  4. File ditulis ke volume /data/uploads/<prefix>/<uuid>.webp.
  5. Next mengirim “key” file ke Go; Go memvalidasi format key sebelum menyimpannya di database.
  6. nginx menyajikan file itu di /uploads/… dengan cache panjang.

4. Model data

Lima tabel inti. Constraint di database adalah pengaman terakhir jika ada bug di kode.

users

Akun dari Google. Menyimpan identitas Google (google_sub), email, nama, foto, dan role:

  • user — pengunjung yang bisa mendaftar event
  • organizer — panitia, terikat satu komunitas
  • admin — admin pusat

communities

Halaman komunitas: slug, nama, tagline, deskripsi, logo, banner, kategori, kota, sosial, status.

organizer_id unik: satu panitia hanya mengelola satu komunitas (fase 1).

events

Milik satu komunitas. Berisi jadwal, lokasi, kuota (boleh kosong = tanpa batas), poster, status (draft, published, cancelled), harga (disiapkan, fase 1 selalu 0), dan link eksternal seperti Instagram.

registrations

Menghubungkan user dan event. Status: pending, approved, rejected, cancelled. Ada aturan unik (event_id, user_id) supaya tidak ada pendaftaran ganda.

email_logs

Catatan pengiriman email. Dipakai untuk menelusuri kalau ada notifikasi yang gagal. Bukan sumber kebenaran status pendaftaran.

schema_migrations

Daftar migrasi SQL yang sudah dijalankan. Migrasi berjalan otomatis saat container API start dan bersifat idempotent.

Relasi

users ──< communities (organizer_id, 1:1 di fase 1)
  │
  └──< registrations >── events >── communities
users >── email_logs

5. Permukaan API (Go)

Semua endpoint memakai prefix /api/v1. Endpoint bertanda 🔒 butuh JWT.

Publik

GET /communitiesDaftar komunitas + pencarian q, filter category, city, paginasi
GET /communities/facetsDaftar kategori dan kota untuk dropdown
GET /communities/:slugDetail komunitas + event mendatang
GET /eventsEvent terbit terdekat
GET /events/:idDetail event
POST /auth/googleTukar ID token Google dengan JWT aplikasi

User 🔒

GET /meProfil dan role
GET /me/registrationsRiwayat pendaftaran sendiri
POST /events/:id/registrationsDaftar event (pending)
POST /registrations/:id/cancelBatalkan pendaftaran sendiri

Panitia 🔒

GET | PATCH /organizer/communityLihat/ubah profil komunitas sendiri
GET | POST /organizer/eventsDaftar/buat event
GET | PATCH /organizer/events/:idDetail/ubah event
POST /organizer/events/:id/publishTerbitkan event
POST /organizer/events/:id/cancelBatalkan event + semua pendaftaran
GET /organizer/events/:id/registrationsDaftar peserta
POST /registrations/:id/approve • /rejectSetujui/tolak peserta

Admin pusat 🔒

POST /admin/communitiesBuat komunitas
GET | PATCH /admin/communities/:idLihat/ubah, termasuk assign panitia lewat email
GET /admin/usersDaftar user

Internal

POST /internal/email-logsDipakai Next untuk mencatat hasil kirim email. Wajib header X-Internal-Secret.
POST /dev/loginHanya aktif jika DEV_LOGIN=true. Untuk development tanpa Google.

7. Cara menjalankan

Dari nol sampai bisa dibuka di browser.

# 1. nyalakan Docker Desktop, lalu dari folder project:
docker compose up -d --build

# 2. isi data demo (sekali per volume)
docker compose run --rm --entrypoint /app/seed api

# 3. buka
http://localhost:8088

Login cepat (mode development):

  • admin@komunifind.test — admin pusat
  • rina@komunifind.test — panitia Jakarta Indie Runners
  • budi@komunifind.test — panitia Bandung Design Circle
  • sari@komunifind.test — user biasa

Perintah harian:

docker compose ps                 # status container
docker compose logs -f api        # log backend
docker compose logs -f web        # log frontend
docker compose up -d --build web  # rebuild setelah ubah frontend
docker compose up -d --build api  # rebuild setelah ubah backend
docker compose down -v            # reset total (hapus DB & upload)

cd api
# PowerShell:

Fokus test backend: kuota, isolasi antar komunitas (tenant), dan siklus status pendaftaran.

9. Batasan & risiko fase 1

Belum ada

Bukan tujuan sekarang

  • Join komunitas (membership).
  • Event berbayar dan payment gateway.
  • Chat, forum, komentar.
  • Notifikasi WhatsApp atau push.
  • Multi-bahasa dan aplikasi mobile native.
  • Komunitas membuat halaman sendiri (masih oleh admin).
Risiko yang diterima

Hal yang bisa bikin repot

  • Sesi 7 hari tanpa refresh; habis berarti login ulang.
  • Email bisa telat/gagal; status tetap benar di halaman user.
  • Satu VPS berarti tidak ada redundansi.
  • DEV_LOGIN harus mati di production.

Keamanan

  • JWT hanya di cookie HttpOnly; tidak pernah dikirim ke JavaScript browser.
  • Setiap request ke Go memverifikasi ulang user dari database; role di token tidak dipercaya buta.
  • Next hanya memeriksa sesi untuk keperluan redirect; otorisasi data dilakukan Go.
  • Endpoint internal butuh X-Internal-Secret.
  • Key file upload divalidasi (prefix, regex, tanpa path traversal).
  • Ganti JWT_SECRET dan INTERNAL_SECRET sebelum deploy.
